# RoboTwin harness v3：视觉定位、几何技能与闭环反馈

代码独立存放在 `robodawn_robotwin_harness_v3`；RoboTwin envs/scripts/config/description 是源码副本，assets 与 Python 环境只读复用。旧 v2 作业和结果不覆盖。本轮仅用 qwen3-vl-plus。最新实验进度与各版本口径见 [评测入口](HARNESS_V3_STATUS.md)。

## 旧配置的主要限制

截至本次抽样，1,980 条决策中 1,572 次执行未成功；子步骤中 648 次 hover 和 910 次 reach 失败，连续相同失败动作重复 454 次。详见 BASELINE_FAILURE_AUDIT.json。这是阶段性快照，旧队列仍在运行。

固定抓取方向、错误视觉落点和缺少持物反馈首先限制了分数。增加决策预算之前，应让技能可执行、有可验证的完成条件，并让失败改变下一步行为。

## 任务需求与设计

| 任务族 | 所需能力 | v3 改进 |
|---|---|---|
| click / press | 小接触面准确落点、沿法向触压 | 图像坐标与深度点绑定，TCP 标定后接近/按压 |
| pick / place / move | 有效抓取、稳定搬运、支撑面高度 | RGB 框内深度聚类、物体主轴估计、多姿态规划预检、接触验证、记忆抓取偏移 |
| 双瓶 / 多物体 | 分臂、保留已完成状态、避免旧落点 | 每动作新观察，左右持物状态与阶段分开，空臂回位 |
| stack / rank | 精确支撑面与多阶段顺序 | 显式 PLACE 支撑面和保持物高度补偿；需要测试精度，不把释放等同于任务成功 |
| rotate / shake / dump | 姿态与重复运动 | TCP 中心旋转、指定方向的有界周期运动 |
| handover / lift_pot | 同步双臂和接触转移 | 当前顺序技能尚不足；需独立补充和验证，不能声称已覆盖 |
| door / microwave / laptop | 关节约束运动、保持接触 | 新增不自动抬起的把手抓持及可见铰链圆弧；笔记本开发案例通过，微波炉等仍需验证 |
| hammer / seal / scan | 工具姿态和功能部位对齐 | 需要功能部位定位及专用控制；不以普通 PICK 冒充已实现 |

## 结构

- Robodawn：保留原 run_loop，Qwen 输出有类型的技能参数和视觉框/接触点。
- Show-Harness：保留原双臂 planner/controller 角色；planner 输出语义阶段，controller 选择宏技能/真实方向动作。单次仅执行一个已验证阶段，成功反馈才推进；连续失败触发重新规划。
- 共用执行层：RGB-D 框内物体点云 → 主轴/高度 → 抓取方向候选 → 机器人路径预检 → 执行 → 接触与位姿反馈。将运动成功、技能成功、官方任务成功分别记录。
- 增加机器人末端位姿移动、旋转、回位、持物展示、抖动、夹爪开合；目标携带物体身份与观察编号。
- 渲染与物理解耦：物理仍逐步推进、官方成功仍逐步检查；降低无用渲染频率，观察时强制刷新图像与深度，并保存过程视频。

## 评测约束

运行时策略只使用图像、相机深度/标定、机器人运动学与接触传感。不得读取对象 actor pose、专家接触点、官方 play_once 轨迹或按任务名执行专家脚本。任务源码审查仅用于了解动作需求和官方成功判定，不向策略传入评分器隐藏状态。

已有 100000 系列官方验证 seed 可用于同场景对照和开发诊断；当前按用户要求先交付每任务一个 episode；尚未运行留出种子测试，是否扩跑由用户后续决定。失败和调试运行全部保留，不能用最佳尝试替换正式分母。最终分数只来自官方 check_success/eval_success。

## 执行时序修正

开发轨迹显示：原地闭爪指令后真实 finger_qpos 仍约 0.035–0.038 m（基本张开），而命令值已经是 closed。原因是零距离 EE 路径只有少量仿真步，驱动器来不及收敛。固定 v3p 在开合动作后推进 100 个物理步、普通运动后 40 步。最新 v3v 进一步发现官方 set_gripper 对每次打开目标限制为增加 10%，因此在 200 个开合收敛步中持续重发夹爪目标；实测闭合后重新打开到 43.6 mm。两版均保留重力补偿与官方逐步成功检测，再读取真实接触。此为执行器时间语义修复；不改变官方成功条件或对象物理属性。

开发中也发现三张相机图同时用于输出坐标时会串视角。当前决策和精定位使用同一 HEAD 图生成 bbox/point，三视图继续保存为证据，并过滤深度不连续的背景；不会把腕部图像坐标当成头部坐标执行。

## 后续开发发现（冻结版独立记录）

- 夹爪等待修复后订书机/积木已能真实持物，但精准放置还会被目的地身份混淆、手臂切换和姿态不可达破坏。
- 定位器必须保留规划器目标身份；不能把 `Cyan` 改名为字面量 `DESTINATION`。对明确颜色的块/垫增加 RGB 颜色区域细化，对大幅冲突的二次定位保留原提案并记录分歧。
- 放置按持物时的 TCP–物体底部视觉偏移做转换，而非固定高度；台面目标使用标定射线与桌面交点。候选朝向要先验证搬运和下降都可达。
- 已通过预检的路径缓存后直接执行，避免二次随机规划把已可达目标再次判成失败。缓存使用前比较机器人当前关节状态，执行一次后失效。
- 垫子对齐规则是开发中的几何启发式，不是已证明通用正确的规则；最终仍由官方成功判定。
- 默认头部相机用于决策与定位，三视图继续记录。腕部相机串坐标的问题作为独立消融项保留，不能宣称多视角必然更好。
- `post_episode_evaluator_diagnostics.json` 仅在策略结束后记录评测诊断状态，不传给策略或模型，也不改变本 episode 的执行。开发 seed 上的调参成绩与留出 seed 成绩必须分列。

## 最新修正的可复现证据

- dev_r 叠方块中，规划器连续指定右手抓绿块，定位器却将 arm 改成 left；v3v 只让定位器细化几何，保留规划器手臂。
- 同一轨迹将 red block 支撑错误标为 table，使放置高度从方块顶部约 0.79 m 投影至桌面约 0.74 m；v3v 从可见实体方块的上表面估计支撑，仍不读取 actor pose。
- 静止手臂和原地夹爪动作重复求解轨迹，浪费 GPU 时间；v3v 保持实测关节，仅对实际末端移动求解轨迹。真实物理检查确认静止手臂保持和夹爪开合，35 项回归检查通过。
- 原 37° 头部视野在移杯任务几乎裁掉整个杯子。独立增强感知实验 v3u 使用同位姿 960×720、60° 头部相机，4 项完成 3 项成功（两项目按铃、Robodawn 移杯）；不得混入标准相机 v3p 分数。
